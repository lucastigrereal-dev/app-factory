# Architecture Overview

This document summarises the high‑level architecture of the **FactoryOS IA** as described in the
blueprint and related artefacts.  The FactoryOS IA is designed as a modular monolithic
application with plug‑in support for automation workflows, AI agents and external integrations.

## Core principles

* **Modular monolith:** The system is a single application divided into well defined modules (e.g. companies,
  diagnostics, routines, scoring, backlog, integrations).  Each module has its own API, data model
  and UI components but shares a common database, authentication and logging infrastructure.
* **Integration runtime:** Automation workflows are not executed inside the core application.  Instead,
  an external orchestrator (n8n) executes workflows based on specifications produced by the Factory.
* **Event‑driven:** Key actions produce events that are consumed by other modules or external services.  The
  event taxonomy is defined in `config/event_taxonomy.yaml`.
* **Governance by design:** Risk levels (R0–R3) and checkpoint gates (CP‑0–CP‑3) are enforced across
  all modules.  High‑risk actions require explicit human approval.

## Data storage

The system uses **PostgreSQL** (via Supabase) as its primary relational database with Row Level
Security (RLS) enabled.  Vector embeddings for AI agents can be stored in **pgvector** or
external vector stores (e.g. Qdrant).  A message queue (Redis) is used for asynchronous tasks.

## AI provider layer

All large language model interactions are routed through a provider layer (via LiteLLM) that
supports OpenAI, Anthropic and Gemini.  Requests are recorded with **Langfuse** for
observability and cost tracking.

## Integration runtime

Workflow specifications generated by the FactoryOS IA are executed in **n8n**, which
provides a low‑code environment for connecting APIs, performing data transformations and
invoking AI agents.  The FactoryOS maintains ownership of the workflow definition, while
the execution environment is decoupled.
